CHAPTER 01

What are we building?

An employee directory that also teaches the complete software delivery journey.

01

A useful application

Add, view, edit and delete employees. Search records, filter by department or status, and see dashboard counts.

02

A repeatable deployment

Package the application in containers, store images in Azure, and run them on Kubernetes.

03

An automated release

Push a commit to main. Azure DevOps builds new images and deploys them to AKS, then checks the application.

In everyday language

Think of a company reception desk. The screen is the form you fill in, the backend is the clerk who checks it, and the database is the filing cabinet. DevOps is how we build, deliver and keep that office running.

What this guide represents

This is a snapshot of the repository on 19 September 2026. It documents the actual local/VM path, the AKS deployment and the current Azure DevOps pipeline. Resource names are project examples, not live status indicators.

Implemented

Containers, AKS manifests, ACR delivery, public-IP ingress, release artifacts and smoke checks.

Needs completion

The pipeline’s pytest command is commented out. Application authentication, production database resilience and a full monitoring setup are not implemented.

Publicly deployed does not automatically mean production-ready. We explain the current lab first, then the changes needed before handling real employee data.

CHAPTER 04

Web basics: what happens after a click?

HTML describes the page, CSS styles it, and JavaScript makes it interact with the API.

  1. Load the interface. The browser asks Nginx for HTML, styles and JavaScript.
  2. Ask for data. JavaScript uses fetch() with relative URLs such as /api/employees.
  3. Route the request. The VM proxy or AKS ingress forwards the API request to FastAPI.
  4. Validate and query. The backend checks the input and talks to PostgreSQL.
  5. Return JSON. The browser receives structured data and updates the screen.

The backend: from input to a database transaction

FastAPI runs the HTTP API. Uvicorn is the server process that listens on port 8000.

The API contract

Method and pathMeaning
GET /api/employeesList records; supports search, department, status, skip and limit.
GET /api/employees/{id}Read one record by its numeric database ID.
POST /api/employeesCreate an employee; returns 201 on success.
PUT /api/employees/{id}Update supplied fields. This implementation permits partial updates despite using PUT.
DELETE /api/employees/{id}Delete a record; returns 204 without a response body.
GET /api/dashboard/statsEmployee count, active count, department count and recent employees.
GET /healthProcess health; does not query the database.
GET /health/dbDatabase connectivity check; returns 503 if unavailable.

A numeric database id and a business identifier such as EMP1001 are different fields. The URL’s {id} uses the numeric key. Invalid input normally produces 422, a missing record 404, and duplicate employee ID or email 409.

In everyday language

The router is the counter, the schema is the form checker, the service is the clerk’s procedure, and the ORM translates the request into the filing cabinet’s language.

CHAPTER 06

The database: data must outlive the container

PostgreSQL holds the durable employee records.

The employees table stores identity, contact details, department, designation, salary, employment status, joining date and timestamps. Unique constraints prevent duplicate employee IDs and emails. Indexes help common lookups; they also cost storage and work on writes. Salary uses a fixed-precision numeric type rather than a floating-point approximation.

Initialization, persistence and migrations

  • Initialization: database/init.sql creates the table and inserts sample rows. AKS mounts a separate copy from aks/database/init-configmap.yaml.
  • First start only: the PostgreSQL image runs initialization scripts when its data directory is empty. Editing the SQL file does not rerun it on an existing disk.
  • Persistence: Compose uses a named volume. AKS uses a 5 GiB PVC with managed-csi storage.
  • Migrations: schema changes need versioned migration steps. SQLAlchemy create_all() is a startup safety net, not a migration system.
  • Passwords: changing a Kubernetes Secret alone does not change the password already stored inside PostgreSQL.
In everyday language

A container is a replaceable office worker. The persistent disk is the filing cabinet. Replacing the worker should not throw away the cabinet. A backup is a separate recoverable copy of the cabinet, not merely the fact that it exists.

The current PostgreSQL Deployment has one replica and uses Recreate. This avoids overlapping database pods during updates, but creates database downtime during replacement. A PVC is not a backup, and one database pod is not high availability.

Start from scratch on your laptop

First make the complete application work locally, before introducing Azure.

Install Git and Docker with the Compose plugin. Clone your own repository and open its root. Use sample data for this lab.

git clone <your-repository-url>
cd employee-management-system-aks
# Fresh checkout only; preserve an existing local .env:
cp -n .env.example .env
# Edit .env: set database settings and a local password.
docker compose up -d --build
docker compose ps
curl -f http://localhost:8080/health
curl -f http://localhost:8080/health/db

Open http://localhost:8080. The host port 8080 maps to Nginx container port 80. PostgreSQL and the backend do not publish host ports. Nginx reaches the backend through Docker’s network using the name backend.

docker compose logs --tail=50 backend
docker compose logs --tail=50 nginx
# Stop the stack while retaining its named database volume:
docker compose down
Check your ignore rules before committing environment files. Keep credentials out of Git. The current repository’s Secret example contains literal credentials; the pipeline deliberately excludes it. Do not use or publish those values for real systems.

Local versus VM

A VM can run the same Compose stack, but you manage its OS, Docker, updates, network rules, storage, backup and uptime. With the current port mapping the VM endpoint is port 8080, unless you intentionally change the mapping or add a fronting proxy.

In everyday language

Compose is a checklist that starts the receptionist, clerk and filing cabinet together on one machine. Kubernetes later manages these components across a cluster.

CHAPTER 12

Availability, scaling and container permissions

Running, ready, healthy and resilient mean different things.

Health checks

Probe / checkEffectCurrent project
Readiness probeRemoves unready pods from normal Service traffic; does not itself restart them.Backend /health on 8000; frontend /health on 8080.
Liveness probeRestarts a container after configured consecutive failures.Both HTTP probes; PostgreSQL uses pg_isready.
Startup probeAllows slow startup before liveness/readiness begin.Not currently configured.
Database smoke checkVerifies backend-to-database connectivity after release.Pipeline calls /health/db; backend /health probes do not check the database.

Requests, limits and HPA

Resource requests guide scheduling and CPU autoscaling. CPU limits can throttle; exceeding a memory limit can lead to OOM termination. Current backend requests are 100m CPU and 128Mi memory, with limits of 300m and 256Mi. Here 100m is one tenth of a CPU core.

The backend HPA targets 70% CPU utilization relative to requests, with 2–5 replicas. It requires metrics-server. More pods need room on nodes: HPA does not itself add nodes. Two pods on one node do not protect against loss of that node.

Rolling updates

Frontend/backend use RollingUpdate with maxUnavailable 1 and maxSurge 1. Kubernetes gradually starts new pods and removes old ones as readiness allows. This can reduce downtime, but does not guarantee zero downtime for every failure or incompatible release. PostgreSQL uses Recreate.

Permissions and writable directories

The application deployments disable privilege escalation, drop Linux capabilities and use a read-only root filesystem. Writable emptyDir mounts provide scratch space. emptyDir survives a container restart inside the same pod but is lost when the pod is removed. It is not database storage.

CHAPTER 13

Public IP, DNS, Ingress and HTTPS

An IP gets the request to the cluster. Routing rules decide which application receives it.

Why direct IP access originally returned 404

The original Ingress matched only employee.aniketghosh.online and aniketghosh.online. A request to an IP sends that IP as the Host header. It did not match those host rules, so the ingress controller returned its default 404.

The current manifest adds a rule with no host for /, /api and /health. It also disables forced HTTPS redirects, allowing direct HTTP access before DNS and certificates are ready.

RouteDestination
/frontend Service port 80 → container 8080
/apibackend Service port 8000 → container 8000
/healthbackend Service port 8000; prefix also covers /health/db
kubectl get ingress -n employee-app
kubectl get svc -n app-routing-system
# Use the current ADDRESS from the ingress output:
curl -i http://<public-ip>/
curl -f http://<public-ip>/health/db

The earlier lab IP was 52.226.225.188; always query the cluster rather than assuming it remains unchanged. The frontend’s own ClusterIP is internal, not your public address.

Add a domain and HTTPS

  1. Set DNS A records for @ and employee to the ingress public IP.
  2. Ensure the Ingress hosts match those domain names.
  3. cert-manager uses the ClusterIssuer and HTTP-01 challenge to prove domain control. The challenge must be publicly reachable on HTTP.
  4. Check Certificate readiness. TLS material is stored in the referenced Kubernetes Secret.
  5. For production, use verified HTTPS and configure redirects deliberately. Remove or isolate the lab catch-all HTTP route if it is not needed.
kubectl get certificate,certificaterequest -n employee-app
kubectl get challenges,orders -n employee-app
# Test domain routing before DNS propagation:
curl -H 'Host: employee.aniketghosh.online' http://<public-ip>/
In everyday language

DNS is the address book, Ingress is the room directory, and TLS is the protected connection. Setting up one does not automatically configure the other two.

The configured domain certificate does not certify direct access to the raw IP. Use HTTP for this lab IP route and the domain for properly verified HTTPS.

CHAPTER 14

Understand one manual AKS release

These are the operations the pipeline later automates.

Prerequisites: an existing AKS cluster and ACR, Docker, Azure CLI, kubectl, image pull permissions, the app-routing ingress controller, cert-manager and the live database Secret. On a new lab, create namespace/configuration and a Secret through your secret-management process before deploying.

az login
az aks get-credentials -g aniketghosh-aks-rg -n aniketghosh-aks
az acr login --name aniketghoshacr

# Use a new release tag each time:
RELEASE_TAG=classroom-001
ACR_SERVER=aniketghoshacr.azurecr.io
docker build -f backend/Dockerfile -t "$ACR_SERVER/employee-api:$RELEASE_TAG" backend
docker build -f frontend/Dockerfile -t "$ACR_SERVER/employee-frontend:$RELEASE_TAG" frontend
docker push "$ACR_SERVER/employee-api:$RELEASE_TAG"
docker push "$ACR_SERVER/employee-frontend:$RELEASE_TAG"

Render and apply the release

Kustomize combines the resources and substitutes the release image references. The helper deliberately excludes secret.yaml so an application release cannot replace the current database credentials with the committed example.

# Run from the repository root in an environment with PyYAML installed.
# Use a fresh output directory for every render.
RELEASE_DIR=$(mktemp -d)/aks
python3 scripts/ci/render-aks.py aks "$RELEASE_DIR"   "$ACR_SERVER/employee-api:$RELEASE_TAG"   "$ACR_SERVER/employee-frontend:$RELEASE_TAG"
kubectl kustomize "$RELEASE_DIR" > "$RELEASE_DIR/rendered.yaml"
kubectl apply --dry-run=server -f "$RELEASE_DIR/rendered.yaml"
kubectl apply -f "$RELEASE_DIR/rendered.yaml"
kubectl rollout status deployment/backend -n employee-app
kubectl rollout status deployment/frontend -n employee-app
kubectl get pods,ingress -n employee-app
Do not run the raw aks/ Secret example against an existing database. The automated delivery path preserves the live employee-secret. For a fresh environment, initialize credentials once and keep the database and Secret consistent.

Infrastructure preparation is a separate setup step. Terraform currently does not enable app routing or install cert-manager. The app-routing add-on can be enabled with az aks approuting enable for the chosen cluster; follow the supported cert-manager installation instructions linked below.

CHAPTER 15

CI/CD: from Git push to a running release

The repository contains a real build-and-deploy workflow, with a test execution gap clearly identified.

A commit pushed to main triggers a run. Saving a local file alone does not. batch: true groups pending changes while a run is active.

What each stage actually does

StageCurrent behavior
TestChecks Python, pg_config and Docker. The pytest execution block is commented out; report publication alone does not test the app.
BuildBuilds backend and AKS frontend images, creates a Python environment for PyYAML, renders image-specific manifests with Kustomize.
Push in BuildAzureCLI@2 authenticates through the ARM service connection, logs in to ACR and pushes images. Runs only for successful main, non-PR builds.
ArtifactPublishes aks-manifests containing the rendered release; excludes the database Secret.
DeployDownloads that run’s artifact, obtains AKS credentials, checks prerequisites, performs a server dry run, applies manifests and waits for rollouts.
Verify in DeployConfirms deployment image references and checks /, /health, /health/db and /api/employees through the public IP.

Important pipeline terms

TermMeaning
Stage / job / stepA major phase / a unit assigned to an agent / an individual task or script.
Agent / poolThe machine executing jobs / a group of available agents. Current pool: new_agent; previous logs named the agent new_agent1.
Service connectionAzure DevOps configuration giving tasks an Azure identity. Current YAML name: new.

Azure Repos pull-request validation requires a branch build-validation policy; a YAML pr: block alone is not sufficient. Pushes to main use the configured CI trigger. Microsoft’s Azure Repos trigger documentation.

In everyday language

The pipeline is a repeatable delivery checklist. The agent is the person doing the work. A service connection is its authorized ID badge. An artifact is the release envelope passed to the deployment step.

CHAPTER 16

Set up the automation and ship a change

Connect the repository, execution machine and Azure permissions once; then push commits.

  1. Register the pipeline. In Azure DevOps, create a pipeline from the repository and choose Existing YAML: .azure-pipelines/aks-deploy.yml.
  2. Prepare the self-hosted agent. Register it in pool new_agent and keep it online. It needs Git, Docker daemon access, Azure CLI, Python with venv support, network access and disk capacity. Current checks also require pg_config. Use a compatible runtime for the restored tests.
  3. Create or authorize the ARM service connection. Its name must match new in the current YAML. Prefer workload identity federation over saved client secrets.
  4. Grant the right permissions. The pipeline identity needs registry push and AKS access. The cluster’s kubelet identity separately needs registry pull access. Registry ABAC mode and AKS authorization mode determine the exact role choices.
  5. Prepare the environment. Create aks-employee-app and authorize the pipeline. Add an Exclusive lock check to make lockBehavior: sequential effective. Add manual approval if required for production.
  6. Check prerequisites. Database Secret, ingress controller and cert-manager must already exist. The pipeline checks them; it does not create the whole Azure platform.
  7. Restore the test gate. Run pytest, publish its report and fail on missing reports. Then run the full workflow and inspect each stage.
git status
git add frontend/index.html
git commit -m "Update employee page heading"
git push origin main

If your branch policy requires review, push a feature branch and merge an approved pull request instead. If a push is rejected because main advanced, fetch/rebase or merge carefully and resolve conflicts before pushing again.

Self-hosted means you operate the agent

When the laptop sleeps or the agent stops, a pipeline may wait for an agent. An already-deployed application continues running in AKS. The agent checks out a specific pushed commit into its work directory; it does not deploy unsaved edits from your project folder. Keep the agent checkout separate from your working copy because checkout can clean/reset it.

For standard ACR RBAC, use AcrPush for the pipeline and AcrPull for the kubelet. Entra-enabled AKS requires appropriate Kubernetes data-plane authorization in addition to permission to retrieve credentials. The complete manifest set includes cluster-scoped resources, so a namespace-only role cannot apply everything. See the setup notes, but use the names in the current YAML.

CHAPTER 17

Verify, observe and roll back

Deployment is the start of operating a service, not the finish.

kubectl get pods -n employee-app -o wide
kubectl get deployments,svc,ingress,hpa -n employee-app
kubectl get events -n employee-app --sort-by=.lastTimestamp
kubectl logs -n employee-app deployment/backend --tail=50
kubectl logs -n employee-app deployment/frontend --tail=50
kubectl rollout status deployment/frontend -n employee-app
kubectl top pods -n employee-app

For a restarting pod, use kubectl logs <pod-name> -n employee-app --previous. Use kubectl describe pod <pod-name> -n employee-app for scheduling, image-pull and probe events. Avoid printing Secret contents while collecting diagnostics.

What to observe in production

Collect request counts, latency, error rates, CPU/memory, restarts, database connections, storage usage and certificate expiry. Centralize logs with request identifiers. Define alerts tied to customer impact and an owner who responds. The repository’s health endpoints do not by themselves implement monitoring or alerting.

Rollback is a planned operation

kubectl rollout history deployment/frontend -n employee-app
# After choosing rollback and checking backend/schema compatibility:
kubectl rollout undo deployment/frontend -n employee-app
kubectl rollout status deployment/frontend -n employee-app

You can also set frontend/backend to the exact tags from a known-good pipeline run. An image rollback does not restore deleted data, reverse a database migration or undo unrelated ConfigMap/Ingress changes. The current pipeline reports failures; it does not automatically roll back.

In everyday language

A successful delivery receipt does not guarantee that every customer will be happy tomorrow. Monitoring watches the service after delivery. Rollback is returning to a known package, while recovery may require restoring data too.

A release path for a production team

Feature branch → PR checks → staging → verification / approval → promote the tested image → production checks

Promote the same tested image between environments instead of rebuilding different contents under the same tag. Define RPO (acceptable data loss) and RTO (acceptable recovery time), then verify them with restore drills.

Five checks for understanding

1. Does saving index.html automatically deploy it?

No. Commit and push to a triggering branch, then the pipeline must complete its build and deployment. The current main trigger watches repository changes, not your editor.

2. Why can two frontend pods have one stable address?

The Service presents a stable internal endpoint and selects ready pods by labels. Ingress exposes the appropriate route through the public entry point.

3. Why might a pod show Running but not Ready?

The process can be running while its readiness probe fails. Kubernetes should not send normal Service traffic to that unready endpoint.

4. Does adding a second database pod automatically create HA?

No. PostgreSQL replication, failover, storage and consistency must be designed. Increasing replicas on this database Deployment is not a replication setup.

5. Why did the pipeline show a green Test job without results?

The test command was commented out. The job checked tools and published a missing-file warning. Stage names do not guarantee that checks execute.

A one-minute project explanation

“We built an employee management application with a JavaScript frontend, a FastAPI backend and PostgreSQL. Docker packages it consistently. AKS runs the containers, Services connect them, and Ingress exposes the website. Azure DevOps builds and pushes versioned images to ACR whenever we push to main, then deploys and checks the release. We learned to diagnose image, permission and routing errors, and we identified the security, testing and resilience work needed for production.”
